# Отчёт по производительности и масштабированию

**Дата проверки:** 5 сентября 2026  
**Прод:** `https://tsehh.ru/`  
**Область:** публичная загрузка сайта, фронтенд Vue, API NestJS, PostgreSQL, MinIO и VPS.

## Краткий вывод

На момент проверки признаков нехватки ресурсов VPS нет. Сервер почти простаивает, свободно около 2.6 ГБ RAM и 47 ГБ диска. Текущие 654 товара для PostgreSQL являются очень маленькой нагрузкой.

Жалоба пользователя могла быть связана с плохим интернетом, но приложение заметно усиливает эту проблему:

- nginx не сжимает JS и CSS;
- начальная страница передаёт около 516 КБ несжатых JS/CSS;
- при переходе в приложение загружаются дополнительные чанки до 1.1 МБ каждый;
- отдельные изображения товаров весят 1–3.4 МБ;
- справочники повторно запрашиваются на разных страницах;
- экран товаров последовательно выполняет пять запросов вместо параллельной загрузки;
- отчёты загружают до 1000 полных записей в браузер и строят графики/Excel на клиенте;
- в БД почти нет индексов под фактические фильтры и сортировки.

Переход «с Axios на TanStack Query» сформулирован неточно. Axios следует оставить HTTP-клиентом с текущими cookie/refresh-interceptor, а TanStack Query использовать поверх него для кэша, дедупликации, повторных запросов и invalidation.

### Ошибка healthcheck — ✅ исправлено

Backend работал и публичный `/api/health` отвечал 200, но Docker помечал контейнер как `unhealthy`.

Причина: healthcheck в `docker-compose.prod.yml` использовал `http://localhost:3000/health`. В Alpine `localhost` выбирает IPv6 `::1`, а Nest слушает IPv4 `0.0.0.0`, поэтому `wget` получал `Connection refused`.

Исправление: healthcheck ходит на `http://127.0.0.1:3000/health` (эндпоинт API не менялся). После обновления compose достаточно пересоздать контейнер backend без `--build`.

## Причины лагов во фронтенде

### Высокий приоритет

1. **Нет gzip/brotli в nginx.**  
   Добавить gzip как минимум для JS, CSS, JSON, SVG и шрифтов. Это обычно уменьшает JS/CSS в 3–5 раз. Brotli можно добавить позднее.

2. **Слишком крупные изображения.**  
   В MinIO найдены WebP размером 3.4 МБ, 2.8 МБ, 1.3 МБ и 1.1 МБ. Формат WebP сам по себе не гарантирует малый размер. Нужны:
   - ограничение длинной стороны;
   - целевой размер/качество;
   - отдельный thumbnail для таблиц;
   - `loading="lazy"` и заданные `width`/`height`;
   - запрет отдавать оригинал 3 МБ в строке каталога.

3. **Тяжёлые библиотеки загружаются до действия пользователя.**
   - `ReportsView` импортирует весь `echarts`;
   - `excelExport.ts` статически импортирует `exceljs`;
   - ExcelJS попадает в route chunk, хотя нужен только после клика «Экспорт».
   
   Нужны модульный ECharts и динамический `import()` ExcelJS внутри обработчика экспорта.

4. **Отчёты тянут большие наборы в браузер.**  
   Продажи и остатки запрашиваются с `limit: 1000`, возвраты могут возвращаться вообще без лимита. При росте данных это даст большой JSON, много Vue-объектов, дорогую сортировку/нормализацию, перерисовку таблицы и графика.
   
   Нужны server-side pagination, отдельные aggregate endpoints для графиков/итогов и серверный экспорт.

5. **Нет кэша серверного состояния.**  
   Pinia stores хранят последний ответ, но каждый `fetch...()` снова идёт в API. Справочники редко меняются, однако категории, склады, комитеты, типы операций и пользователи повторно загружаются при открытии экранов.

### Средний приоритет

6. **ProductsView запускает справочники последовательно.**  
   Сейчас сначала загружаются категории, затем склады, комитеты, типы операций и только потом товары. На соединении с RTT 200 мс это может добавить около секунды даже при мгновенном API. До внедрения TanStack Query эти запросы следует хотя бы объединить через `Promise.all`.

7. **Повторные запросы после mutations.**  
   Создание/изменение/удаление товара, продажи или возврата часто вызывает полную повторную загрузку текущего списка. Иногда store уже обновляет данные, а view дополнительно вызывает `fetchProducts()`.

8. **Лишняя перерисовка графика ReportsView.**  
   Глубокий watcher `normalizedReportData` вызывает `updateChart()`, а смена вкладки и первоначальная загрузка вызывают обновление графика отдельно. Один ответ может приводить к нескольким `clear/init/setOption`.

9. **Утечка resize-listener в ReportsView.**  
   `addEventListener` и `removeEventListener` получают разные анонимные функции. Старый обработчик не удаляется после ухода со страницы. Повторные посещения отчётов накапливают обработчики.

10. **Поиск товаров без debounce.**  
    `ProductsView` вызывает API на событие `input`, то есть примерно один запрос на каждый введённый символ. Поиск не защищён от быстрых повторов и устаревших ответов. TanStack Query отменяет/дедуплицирует только при правильном query key и передаче `AbortSignal`; debounce всё равно нужен.

11. **Dashboard обновляется каждые 5 минут независимо от видимости вкладки.**  
    Таймер удаляется при unmount, что правильно, но лучше использовать `refetchInterval` TanStack Query с остановкой для background tab.

12. **ReportsView дважды загружает отчёт при смене вкладки.**  
    `setReportType()` вызывает `generateReport()`, после чего watcher `reportType` вызывает его ещё раз. Один клик может загрузить два набора по 1000 записей.

13. **ReportsView дважды загружает данные после mutations.**  
    Store после update/delete сам делает refetch с дефолтным `limit: 10`, затем view вызывает `generateReport()` с `limit: 1000`. Первый запрос бесполезен для отчёта.

14. **ProductDetailsView повторно загружает историю из-за deep watcher.**  
    Глубокое наблюдение за всем объектом товара вызывает `fetchProductLogs()` при изменении фото и других вложенных полей. Наблюдать нужно только за `product.id`, а историю обновлять явно после mutation.

## Backend и PostgreSQL

### Индексы

В Prisma-схеме практически отсутствуют индексы под рабочие запросы. Есть только индекс `refresh_tokens.userId` и автоматически созданные primary/unique indexes.

При росте данных нужны как минимум индексы:

- `products(createdAt)`;
- `products(arrivalDate)`;
- `products(categoryId)`;
- `products(warehouseId)`;
- `products(committeeId)`;
- `products(transactionTypeId)`;
- `sales(soldAt)`;
- `sales(productId)`;
- `sales(soldBy)`;
- `returns(returnedAt)`;
- `returns(productId)`;
- `returns(returnedBy)`;
- `audit_logs(createdAt)`;
- `audit_logs(userId, createdAt)`;
- `audit_logs(entityType, entityId, createdAt)`;
- `refresh_tokens(expiresAt)` для очистки.

Поиск `contains + mode: insensitive` по названию, SKU и описанию превращается в `ILIKE '%строка%'`. Обычный B-tree не поможет. Для десятков тысяч товаров нужен PostgreSQL `pg_trgm` и GIN/GiST trigram indexes либо отдельный механизм поиска.

### Запросы, которые не масштабируются

- Dashboard выполняет много запросов параллельно и несколько раз сканирует таблицы.
- Одно открытие Dashboard создаёт ориентировочно 14–17 SQL-запросов с учётом JWT-проверки и problem-sales. При 20 одновременных открытиях это краткий burst примерно 280–340 SQL-запросов.
- Список «долго на складе» возвращается без `take`.
- Returns без `limit` возвращает весь подходящий набор.
- Reports загружает до 1000 полных продаж/товаров со связанными сущностями.
- Media для определения использованных файлов читает массив `images` у всех товаров.
- История товара фильтрует JSON-поля audit log; без специализированных индексов это полный scan.
- Profit alerts сначала получают массив всех подходящих ID продаж, затем передают его в Prisma `IN (...)`.
- Клиентский Excel-экспорт требует сначала загрузить весь набор данных.
- JWT strategy читает пользователя из БД на каждый авторизованный HTTP-запрос.
- Просроченные refresh tokens не удаляются периодической задачей, поэтому таблица растёт постоянно.

### Инфраструктура

- Нет resource limits для контейнеров.
- Нет swap: краткий пик PostgreSQL/Sharp/MinIO может привести к OOM всего VPS.
- Нет ограничения и ротации Docker json-file logs; заполнение диска логами может остановить стек.
- MinIO публикует порты 9000 и 9001 наружу; это вопрос безопасности, но также лишняя поверхность атаки.
- MinIO использует тег `latest`, поэтому обновление может неожиданно изменить поведение.
- `index.html` не имеет явного `no-cache`; после деплоя старый HTML может ссылаться на уже удалённые hashed chunks и давать 404 до hard refresh.
- Объявленный nginx `map $expires` не применяется, потому что отсутствует `expires $expires`.
- Regex статического кэша не включает `.woff`, `.woff2` и `.ttf`.
- `deploy.sh` не выполняет `prisma migrate deploy` и post-deploy smoke test.
- Workflow использует `cancel-in-progress: true`: новый push способен прервать деплой в середине.
- `Dockerfile.proxy` копирует весь `prod.env` в build stage, хотя фронтенду нужны только `VITE_*`; секреты не должны попадать в слои образа.
- Нет измеримых SLO, p95 latency, error rate, slow-query log и мониторинга event loop.
- Один процесс NestJS на 2 vCPU не использует второй CPU для выполнения JS. PostgreSQL, nginx, MinIO и Sharp второй CPU используют, поэтому кластеризация не является первым приоритетом.

## Axios и TanStack Query

### Правильная архитектура

Оставить:

- Axios instance;
- `baseURL`;
- `withCredentials`;
- refresh-token interceptor;
- единое преобразование ошибок.

Добавить `@tanstack/vue-query` поверх `apiService`:

- Query отвечает за server state: загрузка, кэш, stale/fresh, retry, дедупликация, refetch и отмена;
- Axios выполняет HTTP;
- Pinia остаётся для auth, темы, локальных фильтров, состояния dialogs и другого client/UI state.

### Предлагаемые query keys

```text
['me']
['products', normalizedFilters, page, limit]
['product', id]
['sales', normalizedFilters, page, limit]
['returns', normalizedFilters, page, limit]
['dashboard', chartDays]
['reference', 'categories']
['reference', 'warehouses']
['reference', 'committees']
['reference', 'transaction-types']
['users']
```

Роль пользователя влияет на состав полей ответа товара. После login/logout/смены роли нужно очищать или разделять role-dependent cache, чтобы не показать закэшированные manager/admin поля другой роли.

### Начальные staleTime

- справочники: 10–30 минут;
- пользователи/статусы: 2–5 минут;
- товары и карточка товара: 30–60 секунд;
- dashboard: 1–5 минут;
- отчёты: 1–5 минут;
- `refetchOnWindowFocus`: включать выборочно, не глобально для тяжёлых отчётов;
- mutations: invalidation только затронутых ключей, а не всего кэша.

### Порядок миграции

1. Установить QueryClient и VueQueryPlugin.
2. Перенести справочники — максимальная польза при низком риске.
3. Перенести список/карточку товаров и mutations.
4. Перенести dashboard.
5. Разделить отчёты на paginated rows и aggregate endpoints, затем подключить Query.
6. Удалить дублирующий server state из Pinia только после миграции каждого домена.

TanStack Query не исправит большие изображения, несжатые assets, тяжёлые SQL и загрузку 1000 строк. Его нужно внедрять вместе с этими исправлениями.

## Оценка количества товаров

Точное число возможно только после согласованного нагрузочного теста на копии продовых данных. Ниже инженерная оценка, а не гарантия.

### По диску

Сейчас 654 товара занимают около 133 МБ MinIO, то есть примерно 0.20 МБ на товар в среднем по фактическому каталогу. Если оставить половину свободного диска под ОС, Docker builds, БД и backups, грубая вместимость составляет порядка 100–115 тысяч товаров при той же средней плотности изображений.

Это только оценка хранилища. Крупные фото, версии MinIO и локальные backups могут уменьшить её во много раз.

### По приложению

- **До 10 тысяч товаров:** должно работать нормально после gzip, thumbnails и базовых индексов.
- **10–50 тысяч:** обязательны trigram indexes для поиска, server-side отчёты/экспорт, pagination возвратов и ограничение dashboard lists.
- **100 тысяч и больше:** текущая реализация не готова без перечисленных изменений и отдельного нагрузочного теста.

Сейчас фактический предел приложения раньше упрётся не в объём PostgreSQL, а в отчёты `limit: 1000`, клиентский Excel, полнотекстовый `ILIKE`, изображения и сканирование всех товаров в media/dashboard.

## Оценка одновременных пользователей

Нужно различать:

- зарегистрированных пользователей;
- пользователей с действующей refresh-сессией;
- открытые вкладки;
- одновременно активных пользователей, которые прямо сейчас создают запросы.

На текущем VPS и текущих 654 товарах:

- 5–15 одновременно активных операторов должны быть лёгкой нагрузкой;
- 20–50 активных операторов выглядят достижимыми для обычного CRUD после приоритетных исправлений;
- 100+ нельзя обещать без нагрузочного сценария с авторизацией, товарами, dashboard, отчётами и загрузкой изображений.

Это консервативные ориентиры, не результаты benchmark.

Отдельное ограничение — глобальный API rate limit: 300 запросов за 15 минут на один IP. Несколько сотрудников одного офиса обычно выходят через общий публичный IP. Поэтому 3–5 активно работающих сотрудников за одним NAT могут получить 429 раньше, чем VPS приблизится к пределу CPU. Нужны:

- отдельные лимиты для login и обычного API;
- более высокий общий лимит;
- ключ user ID для авторизованных запросов, IP — для анонимных;
- общий store лимитов (например, Redis) только если появится несколько backend instances.

## Как получить доказанный предел

Нужен staging с копией обезличенных данных и сценарии:

1. login;
2. открытие товаров с фильтрами и pagination;
3. карточка товара;
4. dashboard;
5. отчёты по разным периодам;
6. создание продажи/возврата;
7. отдельно — загрузка фото.

Проверять ступенями 5, 10, 20, 50 и 100 virtual users. Критерий стабильности:

- ошибки менее 1%;
- API p95 для списков менее 500 мс;
- mutations p95 менее 800 мс без учёта upload;
- CPU длительно ниже 70–80%;
- RAM без постоянного роста;
- нет pool timeout, 429 и OOM;
- размер и время загрузки страницы проверяются с профилями Fast 4G и Slow 4G.

До такого теста любое одно «максимальное число пользователей» будет предположением.
